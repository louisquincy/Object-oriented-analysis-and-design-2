# Лабораторная работа: паттерн Заместитель ( Proxy )

## 1. Описание проблемы

Приложение «Image Viewer» — просмотрщик изображений. Пользователь открывает папку с фотографиями, видит сетку превью и может просмотреть любое изображение в увеличенном виде.

Без паттерна все изображения загружаются с диска сразу при открытии папки. Каждый объект `RealImage` в конструкторе читает файл, декодирует его и сохраняет пиксельные данные в памяти. При 50 фотографиях это приводит к зависанию интерфейса на ~10 секунд и загрузке всех изображений в оперативную память, даже если пользователь хочет посмотреть только одно фото.

## 2. Решение: применение паттерна Proxy

Паттерн Proxy (заместитель) — объект-прослойка, который контролирует доступ к реальному сервисному объекту, имея тот же интерфейс.

В проекте применён **Virtual Proxy** — заместитель, откладывающий создание тяжёлого объекта до момента, когда он реально понадобится (Lazy Initialization).

В проекте введены:

- **`Image`** — интерфейс сервиса с методами `getPixmap()`, `getFilename()`, `isLoaded()`
- **`RealImage`** — реальный сервис, загружающий изображение с диска в конструкторе
- **`ImageProxy`** — заместитель, хранящий путь к файлу и создающий `RealImage` только при первом вызове `getPixmap()`

Ключевой фрагмент — ленивая инициализация внутри Proxy:

~~~cpp
QPixmap ImageProxy::getPixmap(int width, int height) {
    if (!realImage_) {
        realImage_ = std::make_unique<RealImage>(filepath_);
    }
    return realImage_->getPixmap(width, height);
}
~~~

Клиент (`GalleryWindow`) работает через указатель на интерфейс `Image*` и не знает, взаимодействует он с реальным объектом или с заместителем.

## 4. Сравнение: без паттерна и с паттерном

Без паттерна — все изображения загружаются сразу:

~~~cpp
void GalleryWindow::loadDirect() {
    for (const auto& file : files_) {
        images_.push_back(std::make_unique<RealImage>(file));
        // Каждый RealImage читает файл с диска в конструкторе
        // UI зависает на каждой итерации
    }
}
~~~

С паттерном — создаются лёгкие заместители, загрузка по требованию:

~~~cpp
void GalleryWindow::loadWithProxy() {
    for (const auto& file : files_) {
        images_.push_back(std::make_unique<ImageProxy>(file));
        // Proxy создаётся мгновенно, файл НЕ читается
    }
}
~~~

Дальнейший код (`showThumbnails`, `onThumbnailClicked`) одинаков для обоих вариантов — он работает через интерфейс `Image*`, не зная, что стоит за указателем.

Измеренная разница на 20 изображениях:

| Метрика | Без Proxy | С Proxy |
|---------|-----------|---------|
| Время инициализации | ~4000 мс | ~2 мс |
| Память при старте | Все изображения в RAM | Ничего |
| Отзывчивость UI | Зависает | Мгновенно |
| Загрузка одного фото | Уже в памяти | ~200 мс при первом клике |

## 5. Вывод

Применение паттерна Proxy позволило:

- **Устранить зависание UI** — вместо загрузки всех изображений разом создаются мгновенные заместители
- **Сократить потребление памяти** — в RAM находятся только те изображения, которые пользователь действительно просматривал
- **Сохранить единый интерфейс** — клиентский код работает через `Image*` и не зависит от способа загрузки
- **Обеспечить прозрачность** — замена `RealImage` на `ImageProxy` не потребовала изменений в остальном коде приложения
- **Управлять жизненным циклом** — Proxy сам решает, когда создать реальный объект, и автоматически уничтожает его через `unique_ptr`

Функциональность приложения идентична в обоих вариантах. Разница — в стратегии загрузки ресурсов: eager (жадная) без паттерна и lazy (ленивая) с паттерном.
